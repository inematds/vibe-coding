1

🔌 Qué es MCP (Model Context Protocol)

MCP (Model Context Protocol) es un protocolo que permite que una una sola conexión expone muchas herramientas y acciones. Después de que el agente y el server MCP se conectan, el agente conoce todas las herramientas disponibles y decide por sí solo cuál llamar, cuándo y con qué parámetros. La analogía: es como si Gmail expusiera las acciones «enviar», «redactar» y «buscar correos»; el agente descubre cuál usar.

💡 La idea central

En vez de programar una integración para cada herramienta, conectas un server MCP y obtienes todo un conjunto de capacidades de una vez. El agente empieza a «ver» esas herramientas y a orquestarlas sin que le digas cuál debe usar.

  • •Una conexión: expone varias acciones a la vez.
  • •Autonomía: el agente elige la herramienta y los parámetros.
  • •Patrón: el mismo protocolo sirve para muchos servicios.

2

🗂️ Dónde encontrar servidores MCP

Los servers MCP están en directorios dedicados (como mcp.so) y también aparecen en la búsqueda de GitHub con "MCP server" más el nombre del servicio. Saber dónde buscar —y en qué categoría encaja tu necesidad— agiliza la elección de la herramienta adecuada para la tarea.

🕸️ Web scraping

Extraer y leer páginas web. Ejemplo usado en esta ruta: Firecrawl.

🗄️ Bases de datos

Leer y escribir datos. Ejemplos: Postgres, Supabase.

📁 Documentos

Acceder a archivos y notas. Ejemplos: Google Drive, Notion.

💬 Comunicación

Enviar mensajes y correos electrónicos. Ejemplos: Slack, Gmail.

🎯 Consejo práctico

Antes de instalar, piensa en la categoría: «¿necesito scraping, una base de datos, documentos o comunicación?». Esto reduce la búsqueda y evita instalar servidores que ni siquiera vas a usar (y que consumen contexto).

3

📦 Instalar un MCP server

Para instalar, le das al agente el comando de instalación de la documentación del proveedor; genera el archivo .mcp.json con la entrada del server y un marcador de posición de la clave. Después, te registras con el proveedor, obtienes la API key y la ingresas manualmente en el archivo de configuración, nunca pegándolo en el chat.

Paso a paso de la instalación

1

Copiar el comando de la documentación

En la documentación del proveedor (p. ej., Firecrawl → Integrations → MCP → sección del asistente de código), copia el comando de instalación.

2

Deja que el agente genere el .mcp.json

Pídele que lo instale con ese comando; crea el .mcp.json con la config del server y el placeholder de la clave.

3

Insertar la clave manualmente

Regístrate en el proveedor, copia tu API key y pégala tú mismo en el archivo de config, fuera del chat.

⚠️ Atención: la clave de API

  • ✗Nunca pegues la clave en el chat ni dejes que el agente la inserte.
  • ✗Insértala manualmente en el archivo de configuración: es más seguro.
  • ✗Trata la clave como el acceso a tu tarjeta: si se filtra, cualquiera puede gastar.

🩺 Verificar y diagnosticar

Después de instalarlo, verifica con el comando /mcp: enumera los servers instalados y el estado de cada uno. Si un server recién instalado no aparece, la causa más común no es un fallo de instalación: solo hace falta reiniciar el asistente para que registre los nuevos componentes.

✓ Hazlo

  • ✓Ejecuta /mcp para ver los servers y el estado.
  • ✓Reinicia el asistente si el server no aparece.
  • ✓Confirma la conexión antes de empezar a usar la herramienta.

✗ No lo hagas

  • ✗Creer que la instalación falló sin reiniciar antes.
  • ✗Reinstalar desde cero por impaciencia.
  • ✗Usar la herramienta sin confirmar que el estado sea "conectado".

🎯 Consejo práctico

"¿No apareció? Reinicia." Ese reflejo resuelve la mayoría de los casos de servidores invisibles y ahorra horas de diagnóstico innecesario.

5

🔎 Flujo de investigación con Firecrawl

Con el MCP en su lugar, puedes construir un workflow de investigación de principio a fin: le das un tema, el agente busca en la web con Firecrawl, sintetiza los hallazgos y genera un documento estructurado. Todo reutilizando el framework WAT y un CLAUDE.md WAT como configuración maestra que se lee en cada sesión.

Plan → Build → Run

1

Plan — describe el workflow

En Plan Mode, describe: dar un tema, investigar en la web, encontrar información relevante y actual, compilarla en un brief estructurado y generar un documento en la carpeta temporal mediante Firecrawl. Responde las preguntas (formato de salida, nº de fuentes).

2

Build — generar workflows + tools

El agente genera el .env, el .mcp.json de Firecrawl, la herramienta de conversión de markdown → documento y el workflow de investigación.

3

Run — disparar con un tema

Limpia el contexto y ejecuta con un tema concreto. El agente lee el workflow, realiza las búsquedas en Firecrawl, sintetiza y lo convierte en un documento.

🎯 Lo que especifica el workflow

Un buen workflow de investigación declara los activadores, las entradas, los pasos, un objetivo de fuentes (p. ej., 3-5 búsquedas dirigidas), el manejo de errores y los criterios para evaluar cada fuente; así, el resultado es consistente y confiable.

6

📄 Pipeline de salida

El pipeline de salida separa contenido de formato: el agente primero produce un markdown y después lo convierte en un archivo de documento mediante una herramienta de conversión generada. Esto hace que la salida sea flexible —el mismo contenido puede convertirse a distintos formatos— y fácil de auditar.

pipeline de salida (ejemplo ilustrativo)
tema → busca Firecrawl → síntese
   → brief.md            (conteúdo, markdown)
   → ferramenta de conversão
   → brief.docx          (formato, documento)

⚠️ Atención: la sincronización de los dos archivos

  • ✗Actualizar el markdown no siempre actualiza el documento final.
  • ✗Al pedir un cambio, pide explícitamente que actualice ambos.
  • ✗No te fíes solo de la apariencia del markdown; abre el documento generado.

🎯 Consejo práctico

Cuando cambies el formato (p. ej., cambiar la sección de fuentes de tabla a lista), pide que se propague el cambio al markdown e al documento. De lo contrario, corriges uno y el otro queda desactualizado.

7

♻️ Iteración y autocuración

El primer run rara vez sale perfecto, y está bien. La calidad viene del bucle de iteración: das comentarios específicos ("me gustó la estructura, pero reformatea las fuentes como una lista") y, si algo falla, le pides a la que la propia IA se corrija (autocorrección). Cuanto más específico sea el feedback, mejor será el resultado.

✓ Feedback que funciona

  • ✓"Reformatea la sección de fuentes de la tabla como una lista."
  • ✓"El tono es demasiado formal; hazlo más directo."
  • ✓"¿Se rompió? Revisa el error y corrígelo por tu cuenta."

✗ Comentarios que bloquean

  • ✗"Está mal." (sin decir qué ni dónde)
  • ✗"Vuelve a hacerlo todo." (desecha lo que ya estaba bien)
  • ✗Rendirse ante el primer error en vez de pedir que lo corrijan.

🔁 El loop de autocuración

Si el workflow falla, copia el error y pídele a la IA que lo corrija. Recuerda pedirle que aplique la corrección al workflow y a la herramienta, no solo al resultado; así, la próxima ejecución ya saldrá bien.
